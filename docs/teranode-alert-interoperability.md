# Stock Teranode alert interoperability

The mixed mining lab leaves the alert service disabled by default. An ordinary payment accepted in that configuration establishes block delivery and acceptance. Measuring directive behavior requires the receiving Teranode to have the affected funding output, the same signed alert prefix and a verifiable result for each action.

Teranode v0.16.1 embeds go-alert-system v0.3.3. Its normal alert intake uses the signed libp2p topic and sync protocol. The pinned Teranode gRPC service exposes health. Its schema provides neither a signed-message submission method nor a query for authorized confiscation transaction IDs. The standalone maintained receiver's HTTP endpoints expose health and alert readbacks. The isolated integration uses Teranode's supported genesis key, topic, protocol, private-address and datastore configuration on its stock image. [Teranode dependency](https://github.com/bsv-blockchain/teranode/blob/807f1bea39f52797c72fd157a543e8bb64622510/go.mod) · [Alert service settings](https://github.com/bsv-blockchain/teranode/blob/807f1bea39f52797c72fd157a543e8bb64622510/docs/references/settings/services/alert_settings.md) · [Teranode gRPC API](https://github.com/bsv-blockchain/teranode/blob/807f1bea39f52797c72fd157a543e8bb64622510/services/alert/alert_api/alert_api.proto)

## Reproduce the ordinary signed-state comparison

Build the release and maintained receiver harness from the [qualification runbook](chronicle-qualification.md). Use the Python environment with the pinned functional test dependencies.

```sh
python3 qualification/receiver/build.py
.native/py/bin/python qualification/teranode_alerts.py --binary target/release/scary-node \
  > .native/teranode-positive-alerts.json
.native/py/bin/python qualification/verify_teranode_alerts.py .native/teranode-positive-alerts.json
```

The comparison uses a fresh private regtest network and five disposable lab signing keys. Two unmodified Teranodes bootstrap each other’s Alert Services inside that network. Teranode generates the common funding chain. SV Node imports the exact generated blocks. Scary Node enters near the tip and witnesses the funded output and successor. Three distinct signers sign each notice. One lab publisher sends the bytes to the stock Teranode Alert Service over its isolated GossipSub topic. A separate process passes precisely the same bytes to the maintained receiver and Scary Node. SV Node applies the corresponding height intervals through its authenticated administrative RPC. The run checks the same ordinary payment while frozen, after signed unfreeze and after block inclusion. It compares Teranode's closed SQLite store with the signed bytes and records the per-action processed flags.

The initial comparison recorded three frozen-input rejections and the same released payment on all implementations. All four nodes selected block `59b577996a14421b26f9604492f7f128d8bd2070602f666d03920a089e447f3d`. Verify this receipt with `--outcomes-only`; it retains the signed actions and inclusion block. During one repeat the entrant reached the expected tip without the funded output and returned `input missing from witnessed spendable set`. That attempt did not establish a freeze outcome. The fixture now waits for the entrant to observe its pre-funding boundary and to validate the exact funding block before progressing. [Initial signed observations](evidence/chronicle-teranode-alerts-initial.json)

The fresh complete-history run found the same outcome. The three lab signers authorized the notice, freeze and unfreeze. The first Teranode rejected the signed payment as frozen, SV Node returned `bad-txns-inputs-frozen`, and Scary Node returned `frozen input`. After unfreeze, the second Teranode, SV Node and Scary Node accepted payment `ad2811552239b7775750a2131a62efc00d70b9d021e5b86b483aae797091fe57`. Both Teranodes, SV Node and Scary Node selected inclusion block `7c891969ee61c060a6dc4401deca207e72d72e73ba25e60fbfd2df75a904a23d` at height 105. The first Teranode’s closed SQLite database contained all three signed records marked processed. The maintained receiver reached sequence 3 with zero unapplied records. The receipt includes all 104 common-parent bodies from regtest genesis and the inclusion body for independent replay. [Complete signed comparison and funding history](evidence/chronicle-teranode-alerts.json)

## Reproduce the signed funding prefix from the shutdown-lifecycle run

The funding output in the complete-history comparison above belongs to a different regtest chain than the shutdown-lifecycle run. The following comparison starts fresh stock SV Node v1.2.3 and two stock Teranode v0.16.1 instances. It reads the shutdown run’s public archive and recovers the three distinct signers of its first notice using the lab’s five genesis public keys. Replaying their signatures requires only the published bytes. [Shutdown-lifecycle source archive](evidence/chronicle-waiting-shutdown-dar-history.json.gz)

```sh
funding_history=docs/evidence/chronicle-waiting-shutdown-dar-history.json.gz
.native/py/bin/python qualification/teranode_funding_prefix.py run \
  "$funding_history" .native/teranode-funding-prefix.json
.native/py/bin/python qualification/teranode_funding_prefix.py verify \
  "$funding_history" docs/evidence/chronicle-waiting-shutdown-teranode-prefix.json
```

The driver submits the archived funding blocks to SV Node over local RPC. The second Teranode peers with SV Node over legacy P2P and connects with the first Teranode over their native network. The comparison reads each full wire body back from both Teranode Asset servers. It checks the output on SV Node, reads its status from each Teranode, and broadcasts the original sequence-one freeze on the isolated stock Alert System topic. The SV Node administrative RPC receives the corresponding signed outpoint and interval. Each Teranode's closed Alert System database supplies its processed flag and signed bytes. [Stock UTXO status lookup](https://github.com/bsv-blockchain/teranode/blob/807f1bea39f52797c72fd157a543e8bb64622510/services/asset/httpimpl/GetUTXO.go) · [Stock status codes](https://github.com/bsv-blockchain/teranode/blob/807f1bea39f52797c72fd157a543e8bb64622510/stores/utxo/status.pb.go#L29)

The first attempt hit the stock Asset service’s HTTP 429 limit during body readback, before the freeze. The fresh driver caps readback at eight requests per second per server and honors the stock `Retry-After` response. All three nodes selected parent `4740e2fca602a14d2046ffdf5eef9c3208cba96175bb011757f1e604b9c9605a` at height 107 after one stock legacy-peer redial at height 12. Both Teranodes returned all 107 archived funding bodies byte-for-byte, for 214 successful independent readbacks. SV Node reported two confirmations on the ordinary 100,000,000-satoshi output `706c2d26f50c7cc84d927d00d16d893e6090011083667d43d2fdb3838b2bbce8:0`. [Common funding and freeze receipt](evidence/chronicle-waiting-shutdown-teranode-prefix.json)

Each Teranode returned status 0 before the freeze and status 5 afterward. Each independently stored the exact original sequence-one envelope with its processed flag set. SV Node recorded the same outpoint on its policy and consensus blacklists with start height 108, exclusive stop height 2,147,483,647 and persistent policy enforcement. This comparison ends at the funded, frozen parent. The recipient-spend and maturity measurements in the shutdown-lifecycle archive belong to SV Node and Scary Node. Teranode’s ownership-changing outcome remains unmeasured. ## Scope of the earlier confiscation receipt

The earlier comparison contains all ten signed messages, including the authorization for `af0120d2e50bc1d478db2e19009aab1e696882b6970aea6d09a526a715634c88`. It includes the Scary-originated confiscation block and final recipient block accepted by SV Node. Reconstructing the exact funding state also requires funding transaction `0fb96f4ada0ca71181f9c232934ed58059ce07c558b8c343107a5cfc5ad215e6` and the preceding chain. The original fixture generated those predecessors in an ephemeral SV Node volume. The published receipt includes their identifiers, without the funding body or full chain. [Signed DAR lifecycle](evidence/chronicle-receiver-dar.json)

A fresh SV-authorized run retains the complete funding history. The archived active chain has 1,115 blocks, and the detached recipient branch adds three more. The entrant's Stratum worker originated the authorized confiscation at height 108 and the recipient spend at 1,108. Both SV Node and the entrant rejected the spend at candidate height 1,107. After a reorg, SV Node confirmed the same signed recipient spend again at 1,112. Replaying the archive verifies the funded outpoint, ten signed records through key rotation, both branches, the recipient's signature and final SV active hash. A second fresh stock SV Node replayed all 1,115 active bodies, the three detached bodies, the signed UTXO intervals and authorization. It selected the same final hash, `4747e91f3e7b0ae7f1f4757e28de106effc15d7a0ff78c8de7fa0e9f38040801`. The fixture preserves the bytes for future cross-implementation comparisons. [Fresh SV replay](evidence/chronicle-receiver-dar-replay.json) · [Full SV recovery fixture](evidence/chronicle-receiver-dar-history.json.gz) · [Replay commands](chronicle-qualification.md)

At this Teranode revision, the authorization handler immediately loads the referenced parent output and invokes reassignment in the UTXO store. There is no separate supported authorize-only receipt against the supplied txid. A stored signed message alone establishes receipt. A matched ownership-changing outcome would additionally require a funded frozen input, a per-item application result and an active-chain spend by the new owner. SV Node v1.2.3 remains the reference for that outcome. The independent stock-Teranode result for those exact historical bytes remains unmeasured.
