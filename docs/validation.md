# Recognizing accepted history and checking a spend

Consider a miner joining at height J. In a later block P, a transaction creates an output with a particular amount and locking script. A subsequent miner extends P with proof of work. The entrant recognizes the accepted history on that evidence. On the same branch it can determine whether the witnessed output remains available by checking every input in P after its creation and in every subsequent complete block through its candidate’s parent. It can then verify a new spender’s signature and amounts and include the spend in its own candidate.

Scary Node checks proof of work, linkage and the Merkle commitment before advancing witnessed spend coverage. Ordinary candidate inputs must have a confirmed, evidenced source with a successor or an earlier eligible parent in the same template. Chronicle-era BDK receives the exact script, value and creation height. Unseen inputs leave affected incoming checks deferred. A missing or out-of-order body can leave work paused while the still-verified prefix remains available. The node needs a fresh observation boundary beyond the retained recovery window. The full Teranode processes in the regtest network independently validate Scary Node’s final block. They provide external verification of the experiment. The starting tip comes from native peer announcements. The first observed body establishes the local boundary. From there the node checks linked headers, their work and each complete body. A signed peer identity authenticates a publisher, while a valid successor shows work on the creating block. Neither measurement identifies the economic owner of the hashpower. The operator depends on the peers’ view of the active chain at entry. The node buffers nearby competing bodies and can switch branches within its journal. ## Checking an incoming block with partial state

On each incoming body the node identifies known inputs, unresolved inputs and repeated spends within its evidence. It runs BDK at the actual block height. A complete set of current-era inputs supplies the scripts, amounts and creation heights for whole-transaction validation. On partial transactions it evaluates the evidenced inputs individually. Authorized confiscations use the separate SV Node DAR rules. When every fee is known it checks the coinbase amount against subsidy and fees.

For absolute locktime, the node checks the coinbase and each ordinary payment at the height being connected. A Chronicle mainnet block uses its parent's median time from eleven headers. During entry, a time-based lock that needs missing headers stays unresolved. Each new observation records the applied directive sequence and whether its alert state was current. A gap leaves the final eligibility decision deferred while evidenced script and value checks can still run. The early-Chronicle regtest configuration exercises the reference's switch from block time to parent median at height 576. Mempool admission uses the parent median under SV policy. A transaction that names a producer in the same complete body must spend an available output from an earlier transaction. ## Payments that arrive before the funding block has a successor

A native payment can arrive while its funding block is still the selected tip. If Scary Node knows every input and the payment passes its ordinary admission checks at that tip, the node can hold its bytes until a successor arrives. The payment earns a Stratum job only after the node rechecks the inputs, signatures, fees, current directives and applicable heights on the selected branch. An independent miner may consume a funding output in that successor. In that case, the waiting payment is discarded. An admitted parent can also supply an output to a later transaction in the same validated template.

Both native protocols share one arrival-ordered waiting queue. Its independent limits use `SCARY_MAX_PENDING_TRANSACTIONS` and `SCARY_MAX_PENDING_BYTES`. An operator provisioning both pools should budget up to twice the byte ceiling for raw transactions, plus indexes. An early offer never reserves an input or changes a job. The queue lives in memory and resets on process restart or a fresh observation boundary. Operator status reports its present size and bytes, plus per-transport counts for first retention, promotion and discarded offers. [Native offer handling](../src/mining/waiting.rs)

The recent spend history retains 100,000 consumptions and the difficulty window retains 147 headers. The body and witnessed-output capacities appear in operator status. Reaching a storage or memory budget interrupts readiness. The node preserves unknown outcomes for checks requiring pre-entry evidence.
