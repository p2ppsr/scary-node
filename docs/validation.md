# Recognizing accepted history and checking a spend

Consider a miner joining at height J. In a later block P, a transaction creates an output with a particular amount and locking script. A subsequent miner extends P with proof of work. The entrant recognizes the accepted history on that evidence. On the same branch it can determine whether the witnessed output remains available by checking every input in P after its creation and in every subsequent complete block through its candidate’s parent. It can then verify a new spender’s signature and amounts and include the spend in its own candidate.

Scary Node checks proof of work, linkage and the Merkle commitment before advancing witnessed spend coverage. Ordinary candidate inputs must have a confirmed, evidenced source with a successor or an earlier eligible parent in the same template. Chronicle-era BDK receives the exact script, value and creation height. Unseen inputs leave affected incoming checks deferred. ## Checking an incoming block with partial state

On each incoming body the node identifies known inputs, unresolved inputs and repeated spends within its evidence. It runs BDK at the actual block height. A complete set of current-era inputs supplies the scripts, amounts and creation heights for whole-transaction validation. On partial transactions it evaluates the evidenced inputs individually. Authorized confiscations use the separate SV Node DAR rules. When every fee is known it checks the coinbase amount against subsidy and fees.

The recent spend history retains 100,000 consumptions and the difficulty window retains 147 headers. The body and witnessed-output capacities appear in operator status. Reaching a storage or memory budget interrupts readiness. The node preserves unknown outcomes for checks requiring pre-entry evidence.
