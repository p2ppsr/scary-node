# Recognizing accepted history and checking a spend

Consider a miner joining at height J. In a later block P, a transaction creates an output with a particular amount and locking script. A subsequent miner extends P with proof of work. The entrant recognizes the accepted history on that evidence. On the same branch it can determine whether the witnessed output remains available by checking every input in P after its creation and in every subsequent complete block through its candidate’s parent. It can then verify a new spender’s signature and amounts and include the spend in its own candidate.

Scary Node’s alpha implements this bounded construction. It verifies the wire block’s proof of work and transaction Merkle root before indexing the eligible output and its later consumption. It waits for at least one successor after creation. Its assembly policy admits a small supported set of ordinary signed P2PKH spends. Full history, generalized Script admission and a permanent historical UTXO database are outside the first release. A missing input means that this node cannot include the offered spend. It says nothing about another miner’s ability to check it. Receiving a Merkle proof alone does not establish current unspentness.

The comparative claim is about **additional orphan risk attributable to using this working set**, holding the accepted parent, coverage, validity rules, hashpower and propagation conditions constant. An eligible spend of an actually unspent witnessed output adds no defect merely because the miner lacks unrelated outputs. Ordinary competing tips, stale jobs, publication timing, network isolation and implementation errors remain measurable causes of loss for miners. One accepted block is an existence result. A measured equality of stale rates would require a comparative experiment.

A short greater-work branch can replace the incumbent by using the in-memory undo journal and checking the replacement in parent order. A missing or out-of-order body can leave work paused while the still-verified prefix remains available. The node needs a fresh observation boundary beyond the retained recovery window. The full Teranode processes in the regtest network independently validate Scary Node’s final block. They provide external verification of the experiment. The candidate and its reward and transaction selection originate inside the Rust process.

The starting tip comes from native peer announcements. The first observed body establishes the local boundary. From there the node checks linked headers, their work and each complete body. A signed peer identity authenticates a publisher, while a valid successor shows work on the creating block. Neither measurement identifies the economic owner of the hashpower. The operator depends on the peers’ view of the active chain at entry. The node buffers nearby competing bodies and can switch branches within its journal. The operator supplies the starting history premise.

## Checking an incoming block with partial state

For each non-coinbase input, the second alpha looks up its previous output in the working set. With a supported P2PKH script and its amount, Rust checks the signature. It also checks amount conservation when every input value is available. It records a recent consumption even when it never saw the output’s creation. On the same accepted branch that consumption gives a specific reason to reject a repeated spend. Missing creation evidence, an unsupported signature form or an exhausted verification budget leaves the affected check deferred. When every fee is known, the node bounds the coinbase reward by subsidy plus fees.

The recent spend history is bounded at 100,000 consumptions. The validation window retains up to 147 observed blocks. The alpha budgets 4,096 signature checks per body and restricts Script inspection to its supported transaction sizes and forms. A determinate payment has passed the modeled checks. Unknown historical rules, competing branches, coverage loss and broader Script behavior remain relevant to the assurance of the chain.
