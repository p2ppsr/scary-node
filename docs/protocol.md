# Wire protocol and mining path

The reference target is Teranode v0.16.1. Scary Node uses Rust libp2p to connect using native peer IDs, Identify and signed GossipSub on the network-qualified status, block and subtree topics. A block announcement gives a header and a data service from which the body can be retrieved. The operator’s stable identity belongs to the peer service. It is independent of the payout script.

In observation mode the node records peer notices. When processing bodies it obtains the ordinary serialized BSV block from the peer’s Asset service, binds the header to the announcement, parses transactions and checks the Merkle root and PoW. At publication it keeps the native block and subtree representations retrievable at its own Asset URL before announcing their hashes. A local publish event and acceptance by an independent reference node are separate results. The regtest procedure checks both through the final block hash.

The Stratum V1 job commits to a previous hash, coinbase prefix and suffix, assigned extranonce space, ordered Merkle branches, block version, target bits and time. A worker subscribes, authorizes with a label, receives difficulty and work, and submits an extranonce, timestamp and nonce. Scary Node rebuilds and checks the header. A share that meets the job’s share target records worker effort. A network-target solution triggers block publication. A parent change retires old work. An ordinary transaction refresh preserves valid same-parent jobs, and an applicable directive can retire a job before a worker submits its solution.

The Rust BSV SDK supplies transaction serialization and hashing utilities. Ordinary scripts use the pinned BDK interpreter. The SV TCP transport receives contemporary blocks, retrieves recent missing ancestors and delivers verified local solutions independently from Teranode. [Mixed peer proof](evidence/chronicle-mixed-peers.json) Current-mainnet mining uses the post-fork 144-block chainwork difficulty rule and enough header ancestry to select the endpoint medians. Regtest uses its fixed target. The alpha starts on contemporary BSV and does not implement a historical consensus replay. ## SV wire framing and transfer progress

SV Node v1.2.3 uses a 24-byte header and the double-SHA-256 payload checksum through exactly 4,294,967,295 bytes. Larger messages use the 44-byte extended header with a 64-bit payload length when the peer advertises version 70016 or later. Scary Node tests both header lengths at this boundary without allocating a four-gigabyte fixture. The live large-body receipt measured approximately 12 MiB. A transfer can take longer than ten seconds while writes continue to make progress. The sender releases the mining lock while waiting for TCP and checks the solution’s eligibility before releasing the final byte. If a block read ends early, its header hash identifies the coverage gap when all 80 header bytes have arrived. ## Confirming and serving a solved block

An SV peer can request a local solution by block hash with `getdata`. At the advertised Teranode Asset URL, a peer can request the native block, header, legacy wire body, subtree or individual transactions. A restarted node can answer a subtree-hash request before receiving any request for its block hash. The subtree commits to the ordered transaction IDs with Teranode’s coinbase placeholder.

The node serves an active local solution while its complete body remains in the durable undo journal. It also serves the current solution while publication on the selected parent is eligible. Readiness, active-branch membership and effective invalidations apply when a request arrives, including cache hits. A signed block invalidation withdraws the affected block and its descendants. Evicted historical bodies and blocks mined by other nodes return `notfound` over SV or HTTP 404 from the Asset service.

After sending a solution, each SV connection can request the selected headers after its parent. The first request is due after one second. If the result is still uncertain, the connection allows four further requests, with delays of two, four, eight and sixteen seconds. A returned matching header identifies the peer’s claim. The node requests and validates the body before advancing its selected parent. A solution settles once two successors have been observed. The node can therefore issue a job on the independently observed solution before settlement.

On `/status`, `observation_window_ready` describes the witnessed boundary. `job_wait_reason` and `job_preconditions_met` expose the additional requirements for preparing Stratum work. For example, a node with complete contemporary coverage can be waiting for independent observation of a solution or for an eligible transaction. Each prepared candidate still undergoes verification.

The regtest driver mines two consecutive local blocks through Stratum with one stock SV Node connected. For each solution it verifies that the stock node selects it, the entrant retrieves the peer’s active header and body, and inclusion is recorded before a successor exists. The stock node then adds two successors. After restart, a new peer requests the first solution and a separate HTTP client fetches its native subtree and wire bytes. The driver compares each wire body with the independently stored reference block, checks the requesting peer’s delivery record, and repeats the requests after signed invalidation. The SV delivery record stores the first timestamp for each peer, solution and direction. A completed send, a request for active headers and a returned body each have their own timestamp. Active-chain inclusion and settlement come from separately observed blocks.

The recorded run returned the independent bodies 1,529 ms and 1,904 ms after their respective sends. After restart, the SV requester and the Asset client each recovered the 398-byte first solution. Both interfaces withheld its bytes after the signed invalidation, and the second solution was also withdrawn as a descendant. These timings describe two confirmations on this regtest topology. ## Ordinary peer transactions

An SV Node connection requests announced transaction inventory with `getdata` and accepts `tx` messages after the version handshake. Scary Node skips inventory already in its pending set and duplicate inventory entries in one announcement. The two-frame inbound channel applies backpressure to the socket reader. A native Teranode sends a signed subtree notice with a root and an Asset URL. The default listen-only command counts notices. With `--observe-bodies`, Stratum or shadow assembly active, a separate worker retrieves `subtree_data/{root}`. Its queue holds 16 distinct waiting roots and retains up to three announcing sources per root. The SV-only body-failover mode also suspends native subtree downloads. Missing transaction inventory affects template contents. Block and subtree downloads have separate queues. [Teranode subtree announcement](https://github.com/bsv-blockchain/teranode/blob/807f1bea39f52797c72fd157a543e8bb64622510/services/p2p/message_types.go#L119) · [Asset data stream](https://github.com/bsv-blockchain/teranode/blob/807f1bea39f52797c72fd157a543e8bb64622510/services/asset/httpimpl/GetSubtreeData.go#L43)

The subtree root commits to ordered ordinary transaction IDs and may include Teranode’s coinbase placeholder. Scary Node checks the entire root before offering the first transaction. It reads both ordinary wire and extended transaction encodings. Previous locking scripts and amounts supplied in an extended transaction are discarded. Both peer transports run the same witnessed-input checks and BDK policy and candidate checks as local transaction admission. An unknown input, a conflicting spend or a policy failure excludes the transaction from the template. An output created at the current tip needs an observed successor before an ordinary spend of it qualifies. [Teranode fixture for the placeholder and transaction bytes](https://github.com/bsv-blockchain/teranode/blob/807f1bea39f52797c72fd157a543e8bb64622510/services/subtreevalidation/check_block_subtrees_subtreetocheck_overwrite_test.go#L111)

The operator can inspect `mining.peer_transaction_intake` in `/status` for process-lifetime counts of received transactions admitted, already pending or ineligible per transport. `peer.subtree_queue_full` counts notices dropped under backpressure. The next announcement of an unqueued root can schedule a new download. A subtree fetch failure leaves the node’s block coverage intact.

Run the ordinary intake proofs from the repository root with Docker, a release binary and the Python environment used by the [Chronicle qualification](chronicle-qualification.md). Each driver starts its own fresh regtest store. The wallet submits a payment to the stock node after Scary Node observes the funding block and a successor. The worker checks the payment’s Merkle branch before returning proof of work through Stratum. The issuing stock node then selects the entrant’s block and mines its successor.

The Teranode Asset endpoint accepts `?wire=1` for the complete original block and a no-query form with an eight-byte blkdat prefix. A four-byte length in that prefix limits only the no-query form. If the calculated length exceeds its field, the node returns HTTP 406 for that representation. The native block, subtree and wire routes remain eligible. Both blkdat and ordered subtree transaction batches stream immutable slices of the solved bytes. The optional length is tested at its exact limit without allocating a four-gigabyte block.
